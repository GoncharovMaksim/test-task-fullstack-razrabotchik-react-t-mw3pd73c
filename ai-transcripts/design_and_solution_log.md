# Лог решения и этапы проектирования: Мини-CRM «Объекты и задачи» (2B Studio)

## 1. Постановка задачи и анализ требований

**Цель:** Создать корпоративную систему мини-CRM для строительной компании с разграничением ролей («Постановщик» и «Исполнитель»), управлением объектами (стройками) и жизненным циклом задач со строгим контролем переходов и защищенной историей.

### Ключевые требования:
1. **Роли и видимость:**
   - Постановщик (Руководитель): видит все объекты и задачи, создает/редактирует/удаляет объекты и задачи, назначает исполнителей, принимает задачи или отправляет на доработку.
   - Исполнитель (Подрядчик / Мастер): видит ТОЛЬКО свои задачи и ТОЛЬКО те объекты, в которых у него есть назначенные задачи. Чужие задачи и чужие объекты физически скрыты.
2. **Жизненный цикл задачи (Конечный автомат / State Machine):**
   - `[init]` -> `Новая` (new): только постановщик при создании задачи.
   - `Новая` -> `В работе` (in_progress): только назначенный исполнитель.
   - `В работе` -> `На проверке` (in_review): только назначенный исполнитель.
   - `На проверке` -> `Принята` (accepted): только постановщик.
   - `На проверке` -> `На доработке` (rework): только постановщик, комментарий строго обязателен!
   - `На доработке` -> `В работе` (in_progress): только назначенный исполнитель.
   - Другие переходы запрещены.
3. **Безопасность (Security at Database Level):**
   - Row Level Security (RLS) в PostgreSQL.
   - Проверка переходов на триггере в БД (`validate_task_status_transition`).
   - Неизменяемый журнал истории (`task_history`), запрет UPDATE/DELETE.
   - Отключение публичной регистрации.

## 2. Архитектура решения

1. **Frontend:** Next.js 14 (App Router) + React 18 + TypeScript (strict mode) + Tailwind CSS + Lucide Icons.
2. **Database & RLS (Production):**
   - PostgreSQL / Supabase SQL-миграции (`supabase/migrations/20261105000000_init_crm.sql`).
   - Функция проверки роли с `SECURITY DEFINER`.
   - RLS-политики на `objects`, `tasks`, `task_history`, `profiles`.
   - Триггер валидации переходов перед `UPDATE OF status ON tasks`.
   - Триггер автоматической записи в историю после `INSERT` и `UPDATE`.
   - Исходные демонстрационные данные в `supabase/seed.sql`.
3. **Standalone / Live Demo Engine:**
   - Изолированный движок `CRMStore` (`src/lib/storage.ts`), в точности эмулирующий серверные RLS-правила, проверку переходов и аудит-логирование с поддержкой `localStorage`.
   - Позволяет моментально запускать и тестировать решение на Vercel без обязательной привязки сторонних платных/бесплатных баз.
4. **Тестирование:**
   - 41 автоматический тест на Vitest (юнит-тесты переходов, тесты RLS, интеграционные тесты UI).
   - 100% прохождение тестов.

## 3. Этапы разработки

- **Этап 1:** Анализ ТЗ и формализация бизнес-правил, состояний и ограничений безопасности.
- **Этап 2:** Проектирование схемы базы данных, написание миграций `supabase/migrations/` со строгими RLS-политиками и триггерами переходов.
- **Этап 3:** Написание типов TypeScript (`src/types/index.ts`) и чистой функции конечного автомата (`src/lib/transitions.ts`).
- **Этап 4:** Реализация хранилища данных `CRMStore` с зеркалированием RLS-политик и авто-логированием истории.
- **Этап 5:** Разработка UI: экран авторизации, переключатель ролей, список объектов, карточка объекта, карточка задачи с кнопками действий и таймлайном истории, экран «Мои задачи», модальные окна создания и редактирования.
- **Этап 6:** Написание 41 теста (юнит, RLS, UI-компоненты).
- **Этап 7:** Контейнеризация (Dockerfile + docker-compose.yml), подготовка подробного README и деплой на Vercel.
