## 1. Объяснение для руководителя-непрограммиста (ТЗ 4.3)

### Как устроена система
Система представляет собой **«цифровой сейф с изолированными рабочими зонами»**. В строительном бизнесе критически важно, чтобы подрядчики не знали финансовые подробности чужих объектов, не читали чужую переписку и не могли случайно или намеренно повредить данные компании:
1. **Руководитель (Постановщик):** Имеет обзорную панель управления всеми строительными площадками города. Он ставит задачи, назначает ответственных мастеров, утверждает выполненные этапы либо возвращает их с указанием конкретных замечаний.
2. **Мастер / Бригадир (Исполнитель):** Заходит в систему и видит исключительно порученные лично ему участки работ. Для него нет постороннего информационного шума: он берет задачу «В работу», выполняет ее и жмет «Отправить на проверку».

### Как защищены данные и почему интерфейсу можно доверять
В обычных простых программах правила доступа часто настраивают только в визуальной части (просто скрывают кнопку). Если хитрый пользователь зайдет через панель разработчика браузера или отправит прямой запрос к серверу, слабая программа выдаст все секреты.

В нашем проекте безопасность реализована по стандарту **Row Level Security (RLS) прямо на уровне ядра базы данных PostgreSQL**:
- **Физическая изоляция строк:** Сама база данных перед тем, как отдать хоть одну строчку, сверяет цифровой пропуск пользователя. Если мастер Иванов запросит «дай мне все объекты компании», база данных аппаратно отфильтрует строки и вернет только те стройки, где у Иванова есть задачи.
- **Серверный контролер статусов:** Нельзя «перепрыгнуть» статус. Даже если отправить хакерский запрос с командой «пометить задачу принятой», база данных отклонит операцию, так как право на прием имеет только авторизованный руководитель.

### Что исполнитель НЕ может сделать:
1. **Не может увидеть чужие стройки и задачи:** Исполнитель не увидит объекты, к которым он не прикреплен, а также задачи других бригадиров.
2. **Не может сам себе утвердить задачу:** Статус «Принята» доступен только руководителю.
3. **Не может изменить условия задачи:** Исполнитель не может переименовать задачу, сменить адрес стройки или переназначить исполнителя.
4. **Не может подделать или удалить историю:** Любое изменение статуса фиксируется несгораемой записью с точным временем и автором. Функции удаления или перезаписи истории заблокированы в базе данных.
5. **Не может зарегистрировать лишний аккаунт:** Открытая регистрация отключена.

## 2. Список решений и допущений (ТЗ 4.4)

1. **Двухуровневая модель работы (Dual-Mode):**
   - **Production Supabase:** В директории `supabase/migrations/` содержатся полноценные SQL-скрипты миграций с RLS-политиками, триггерами проверки переходов и таблицей `task_history`. При наличии ключей `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` система подключается напрямую к Supabase.
   - **Standalone Demo Engine:** Для гарантированной работы демо на Vercel (без зависимости от лимитов и приостановок бесплатных облачных БД) реализован изолированный стор `CRMStore` с точной эмуляцией RLS и валидатора переходов на клиенте и поддержкой сохранения состояния в `localStorage`.
2. **Конечный автомат переходов статусов (ТЗ 2.3):**
   - `Новая` -> `В работе` (только назначенный исполнитель)
   - `В работе` -> `На проверке` (только назначенный исполнитель)
   - `На проверке` -> `Принята` (только постановщик)
   - `На проверке` -> `На доработке` (только постановщик, комментарий строго обязателен)
   - `На доработке` -> `В работе` (только назначенный исполнитель)
   - Любые другие комбинации строго отклоняются как в UI, так и в логике валидации.
3. **Обязательность комментария при возврате на доработку:**
   Интерфейс блокирует отправку без комментария, валидатор возвращает флаг `requiresComment: true`, а в SQL-триггере прописана проверка `NEW.rework_comment IS NOT NULL AND length(trim(NEW.rework_comment)) > 0`.
4. **Управление объектами и задачами постановщиком:**
   Постановщику предоставлены полноценные модальные окна редактирования и удаления объектов, а также редактирования описания/исполнителя задач.

## 4. Локальный запуск и тестирование

### Вариант 1: Запуск через Node.js / npm

1. Склонируйте репозиторий:
   ```bash
   git clone https://github.com/GoncharovMaksim/test-task-fullstack-razrabotchik-react-t-mw3pd73c.git
   cd test-task-fullstack-razrabotchik-react-t-mw3pd73c
   ```

2. Установите зависимости:
   ```bash
   npm install
   ```

3. Запустите автоматические тесты (41 тест):
   ```bash
   npm test
   ```

4. Запустите проект в режиме разработки:
   ```bash
   npm run dev
   ```
   Откройте [http://localhost:3000](http://localhost:3000) в браузере.

5. Сборка production-версии:
   ```bash
   npm run build
   npm start
   ```

### Вариант 2: Запуск в Docker Compose

Запуск одной командой:
```bash
docker compose up --build
```
Приложение будет доступно по адресу [http://localhost:3000](http://localhost:3000).

## 5. Подключение к облачному Supabase

Для подключения реального инстанса Supabase:
1. Создайте бесплатный проект на [supabase.com](https://supabase.com).
2. Выполните SQL-скрипт из `supabase/migrations/20261105000000_init_crm.sql` в SQL Editor Supabase.
3. Выполните сидирование данных из `supabase/seed.sql`.
4. Создайте файл `.env.local` в корне проекта:
   ```env
   NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=your-anon-key
   ```
5. Перезапустите приложение (`npm run dev`).
